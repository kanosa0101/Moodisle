## 🎯 2. 系统概述

Moodisle 是一款“情绪即天气”的陪伴式待办与专注应用。用户录入真实待办并选择情绪属性后，领域逻辑生成对应的天气伙伴；完成待办会推进伙伴成长、气候、资源和成就。专注会话按秒推进；回廊以本地生成的迷宫状态运行；岛屿、图鉴、云游和成长页读取同一份玩家状态。

系统以 `GameState` 作为主要内存状态，由 `GameCore` 执行规则，`GameController` 协调页面、领域内核、生命周期和存档。生产入口在 `app/lib/main.dart` 创建 `MoodisleApp(repository: SqliteGameRepository())`。关系存储通过 repository 隔离，页面与领域引擎不直接访问 Drift 表。

**依赖规则：**表现层依赖 `GameController`，不直接写 SQLite；`GameController` 负责页面协调，并调用 `GameCore`、`GameRepository`，同时直接编排 `EcoSim` 状态重建和活动 `MazeRun` 的步进/撤销等运行时操作；`GameCore` 与领域实体不依赖 Flutter、Drift 或平台 UI；持久化适配层负责在关系表和领域状态之间转换。`MoodisleAudioService` 属于表现侧能力，不参与领域结算。

### 3.2 架构决策与评价

| 决策 | 选择理由 | 成本与评价 |
| --- | --- | --- |
| Flutter/Dart 单代码库覆盖 Web、Android、iOS | 尽量保持页面、领域规则、媒体资源和存档格式一致，减少平台重复实现。 | 浏览器存储、操作系统生命周期、签名与音频差异仍需各平台验收；统一源码不等于运行行为自动一致。 |
| `GameCore` 与 `GameController` 分工 | 领域规则集中在 Dart 内核，controller 负责 UI 通知、计时和应用流程；主要规则可独立测试。 | controller 还直接协调 `EcoSim`、活动 `MazeRun`、恢复与存档，属于有意保留的轻量门面；继续增加功能时应避免把规则和平台 IO 都堆入 controller。 |
| `GameRepository` 隔离 SQLite，保留 JSON v2 兼容路径 | Drift 关系表适合本地结构化保存；JSON 用于手动交换、旧档迁移和数据库故障降级。 | 两种存储并存增加恢复路径复杂度；SQLite 完整映射/升级样本仍需直接测试。详见 [数据库设计](10-数据库设计.md)。 |
| 本地单机、事务式全量快照 | 不需要账号和服务端，数据路径简单；SQLite 事务避免半份快照被提交。 | 不支持云同步或多档案；状态变大后全量替换的写入成本需要重新评估。 |

**综合判断：**当前规模下，这种分层在跨端复用、领域规则可测性和离线部署之间较合适；主要结构性风险是 controller 职责继续膨胀、两条存储路径的故障行为差异，以及数据库迁移/平台存储缺乏直接验收。当前不需要预先引入远程服务、复杂状态管理框架或插件化模块；应以补齐 repository 和目标设备验收证据作为近期质量改进。

## 🔁 4. 关键运行链路

### 4.1 启动与存档恢复

~~~mermaid
sequenceDiagram
    accTitle: Startup And Save Restoration
    accDescr: The app constructs its controller and starts asynchronous restore. SQLite is read first. If empty, JSON v2 is validated and migrated. Database errors switch to the legacy JSON path and are surfaced as a recovery notice.

    actor User as 玩家
    participant Main as MoodisleApp / AppShell
    participant GC as GameController
    participant Repo as SqliteGameRepository
    participant DB as Drift / SQLite
    participant Store as SaveStore / SaveCodec
    User->>Main: 打开应用
    Main->>GC: 创建 controller 并注入 repository
    GC->>Repo: load()
    Repo->>DB: 读取玩家档案及状态表
    alt SQLite 中存在档案
        DB-->>Repo: 关系表记录
        Repo-->>GC: DecodedSave(GameState, MazeRun)
    else SQLite 为空
        Repo-->>GC: null
        GC->>Store: load() 并校验 JSON v2 主档/备份
        alt 发现有效旧档
            Store-->>GC: 有效 JSON v2 文本
            GC->>GC: importSaveJson() 解码并恢复领域状态
            GC->>Repo: save() 执行首次迁移
            Repo->>DB: 事务式写入完整状态
        else 无有效旧档
            GC->>GC: 使用新档默认状态
        end
    else SQLite 读取异常
        GC->>Store: 切换到旧存档恢复路径
        GC->>Main: 设置恢复提示
    end
    Main->>GC: 等待 ready 完成
    GC-->>Main: 恢复完成，显示应用页面
~~~

启动时 `GameController` 创建领域内核、确保当天状态并重建生态，再异步恢复存档。生产入口注入 SQLite repository；测试或未注入 repository 的实例仍可走 JSON 路径。SQLite 首次初始化失败或存取失败时会尝试旧 JSON 路径并设置用户提示。降级存档的最新程度取决于最近一次成功写入的 JSON，因此 JSON 导出仍是用户可控的备份方式。

~~~mermaid

    accDescr: A page invokes GameController. GameCore and domain engines mutate the in-memory game state and return events. The controller notifies the UI, schedules a debounced save, and writes a full snapshot in one SQLite transaction. Lifecycle pause requests an immediate flush.

    actor User as 玩家
    participant Page as Flutter 页面

    Core->>State: 校验并更新领域状态
    Core-->>GC: 返回 GameEvent 列表
~~~

`GameController` 的业务入口覆盖待办、收服/培育、专注、迷宫、签到、每日任务、云游、商店和存档导入导出。领域事件只描述规则结果或待演出的奖励；页面读取更新后的领域状态并负责动画、弹窗及音频。专注活动期间 controller 用 1 秒 timer 推进领域时钟；移动端锁屏时以 `screenLocked` 阶段保留计时起点，应用切换则保存 `glancing` 暂停态，恢复后分别按阶段补算或继续。

## 🔌 5. 模块接口与外部交互

### 5.1 模块内接口

| 调用方 → 提供方 | 接口形式 | 契约 |
| --- | --- | --- |
| 页面 → `GameController` | Dart 方法调用与 `ChangeNotifier` | 页面提交用户意图；controller 更新状态后通知监听者。页面不保存领域规则副本。 |
| `GameController` → `GameCore` | 同步 Dart 方法 | 提供操作参数；规则改变 `GameState`，返回 `GameEvent` 集合或迷宫运行事件。 |
| `GameController` → `GameRepository` | 异步 `Future` 接口 | `load()` 返回 `DecodedSave?`；`save(GameState, {MazeRun?})` 保存玩家状态与活动回廊。 |
| repository → Drift database | Drift 查询、批处理与事务 | repository 将领域对象映射成表记录；每次完整快照写入一个 SQLite 事务。 |
| 页面/应用壳 → 音频服务 | `MoodisleAudioService` 方法调用 | 页面事件触发 SFX；应用状态和天气更新 BGM；音频不改变游戏状态。 |

### 5.2 外部接口

| 外部对象 | 交互方式 | 数据/限制 |
| --- | --- | --- |
| Android / iOS 文件系统 | `drift_flutter` SQLite 执行器；JSON 兼容存储使用应用文档目录 | 数据处于应用沙箱；本地数据留存受平台卸载行为影响，需用户另行导出备份。 |
| Web 浏览器 | Drift SQLite WASM + `drift_worker.js`，存储后端由浏览器能力与 Drift 运行时选择 | 本地持久化模式受浏览器和隐私设置影响；禁用持久化 API、刷新恢复和多标签一致性需按目标浏览器验收。 |
| Flutter 应用生命周期与锁屏 | `WidgetsBindingObserver` 处理 `hidden`、`paused`、`resumed`；`moodisle/focus_lifecycle` MethodChannel 接收原生锁定/解锁信号 | `inactive` 单独不暂停；应用切换时立即暂停，短暂过渡窗口内到达的原生锁屏信号可将状态升级为锁屏计时。Android 使用 `ACTION_SCREEN_OFF` / `ACTION_USER_PRESENT`，iOS 使用受保护数据锁定/解锁通知；Web 页面隐藏时暂停。解锁后若仍在其他应用，专注从解锁时刻暂停；锁屏阶段按 `lastTickAt` 补算，不保持屏幕常亮。原生信号依赖运行中的进程，进程被系统终止后无法从当前桥接恢复准确解锁时刻。 |
| 音频输出 | `just_audio` 播放随包 WAV/音乐资源 | 当前不需要外部音频服务；权限、静音和后台行为仍按平台进行实机检查。 |
| 用户存档交换 | JSON v2 编解码 | 用户主动导出/导入；编解码版本与 SQLite `schemaVersion` 独立。 |

当前 `pubspec.yaml` 中运行依赖包括 Flutter SDK、Drift、`drift_flutter`、`path_provider` 和 `just_audio`。工程代码未设置业务后端 HTTP API、账号系统或远程同步接口。

## 💾 6. 数据与状态设计

- **领域状态：** `GameState` 是运行中游戏状态的聚合对象；任务、伙伴、资源、气候、专注、每日成长、云游/社交等由领域实体表达。活动回廊 `MazeRun` 通过单独参数保存与恢复。
- **状态规则：** `GameCore` 协调领域引擎并更新状态；派生形态、等级和迷宫规则优先从源状态与配置计算，避免 UI 重复计算或保存派生副本。
- **自动持久化：** 玩家状态变化后约 2 秒合并写入；`flushSave()` 用于生命周期边界的即时写入请求。SQLite repository 在单个事务中替换完整关系化快照。
- **兼容格式：** SQLite schema 当前为 v1；JSON 存档格式为 v2，负责导入/导出和首次从旧存档迁移，两种版本独立演进。
- **目录数据：** 情绪、物品、每日任务与纪念品目录由应用配置播种；schema 中的部分关联由外键约束，单机单档案与活动迷宫的若干关联仍由 repository 约定维护。

数据库的关系图、29 张表字段、主外键、约束、版本迁移与完整性缺口见[数据库设计文档](10-数据库设计.md)，本文件不再重复字段级定义。

## 🚢 7. 平台部署与构建

### 7.1 运行形态

| 平台 | 运行形态 | 本地持久化实现 | 当前验收边界 |
| --- | --- | --- | --- |
| Web | Flutter Web 静态资源在浏览器中运行；SQLite WASM 与 worker 随包部署 | Drift Web 存储后端按浏览器能力选择 | 浏览器刷新恢复、隐私模式、多标签写入要在目标浏览器单独验收；静态构建通过不代表这些场景通过。 |
| Android | Flutter Android 应用 | Drift 原生 SQLite；存档位于应用私有区域 | 已有 2026-10-01 用户设备验收记录；SQLite 接入后的当前包是否完成重新安装验收，以 docs/09 最新记录为准。 |
| iOS | Flutter iOS 应用壳；Windows 开发机通过 GitHub macOS runner 构建 | Drift 原生 SQLite | 2026-10-14 无签名 Release 编译及包内核对通过；签名 IPA 和 iPhone 真机行为尚无验收记录。 |

三端共享核心代码和资源，平台差异集中在 Flutter embedding、SQLite 执行器、浏览器存储、应用生命周期与构建签名配置。

### 7.2 持续集成与发布构建

- `.github/workflows/ci.yml` 在推送 `main` 或针对 `main` 的 pull request 时运行 Ubuntu/Linux 门禁：依赖解析、静态分析、Flutter 测试、迷宫性能门禁、资产校验、跨平台一致性、清洁室词扫描与资产台账审核。
- `.github/workflows/ios-build.yml` 只有 `workflow_dispatch` 手动触发，使用 macOS runner；默认产出无签名 app，选择签名 IPA 时需要配置签名材料。工作流不因普通推送自动触发，以控制 macOS 构建次数。
- 主要本地命令见 [多端技术架构](05-多端技术架构.md) 与 [验收指南](09-验收指南.md)。本次仅新增设计文档，不修改应用代码或平台构建配置。

## 🛡️ 8. 质量属性与设计约束

| 属性 | 当前设计与实现 | 验收/边界 |
| --- | --- | --- |
| 离线能力 | 规则、存档和媒体资源在客户端；原生应用无需业务服务器即可运行。 | Web 首次加载需静态资源托管可用；不能把 Web 首次加载描述为完全无网络。 |
| 状态一致性 | UI 观察同一 controller 状态；领域变更集中在 `GameCore`；关系快照以 SQLite 事务写入。 | 游戏规则单测不能替代 repository 的端到端数据库往返和迁移测试。 |
| 故障恢复 | SQLite 读取/写入异常时切换 JSON 兼容路径并显示恢复提示；JSON 存储保留有效主档备份。 | 降级数据可能落后于 SQLite 最近状态；用户需保留导出的 JSON 备份。 |
| 可移植性 | Web、Android、iOS 共用 Flutter 页面、领域逻辑、资源和 repository 契约。 | 操作系统存储、浏览器 API、生命周期和签名属于平台边界，需单独验收。 |
| 隐私 | 当前为本地单机模型，没有应用账号、业务后端或云同步。 | 本地数据库没有应用层加密设计；应依赖设备/浏览器的本地隔离能力，使用者自行管理导出的存档文件。 |
| 可维护性 | 规则、UI、应用协调、存储 adapter 分层；重要状态通过明确的 Dart 类型和事件表达。 | 新增 SQLite 表或字段时必须同步 schema 版本、升级策略、数据库文档与迁移样本。 |
| 性能 | 专注用轻量 1 秒心跳；存档做约 2 秒 debounce，并批量/事务化写入。 | 当前没有端到端响应时延 SLA；迷宫预算以 CI 性能门禁记录为准。 |
| 可访问性 | 页面使用 Flutter 组件并提供主题、文字、图标等本地资源。 | 当前文档没有完整的屏幕阅读器、语义标签、系统字号和色彩对比专项验收报告。 |

## ⚠️ 10. 已知限制与演进约束

1. **单档案约定：**若未来支持多个玩家档案，应把若干 `id = 1` 单例表迁移为带 `profile_id` 的关系，并增加外键约束和历史数据迁移。
2. **快照保存：**当前全量状态快照实现简单、事务边界明确；若状态规模或写入频率显著增加，再评估增量持久化，并保留崩溃恢复验证。
3. **数据库升级：**schema v1 的 `onUpgrade` 目前没有历史迁移步骤。任何 schema 修改都需增加版本迁移并用旧版本数据库样本验证。
4. **浏览器持久化：**浏览器可能拒绝或清理本地持久化，浏览器间表现不同；目标浏览器和隐私模式测试属于发布验收，而不是构建门禁的推论。
5. **平台验收：**iOS 无签名构建仅证明可编译和包内信息可核对；签名、安装、生命周期、音频和实际界面仍需 iPhone 验收。
6. **安全边界：**当前没有账号授权、服务端访问控制或应用层数据库加密；不要把本地数据库当成跨设备备份或防物理提取的安全存储。
